
# منهجية المراقبة والتنبيهات في وميض

الهدف: أي عطل يصيب مستخدمًا — على الهاتف أو الكمبيوتر — يصل إلى بريدك خلال دقائق،
مع معرّف تقرير يمكن تتبعه.

## 1. القنوات (قناة واحدة لكل منصة)

| المنصة | الأداة | أين تُضبط تنبيهات البريد |
|---|---|---|
| ويندوز (Wameed.exe) | **Sentry** — المشروع `wameed-windows` | لوحة Sentry → Alerts |
| أندرويد | **Firebase Crashlytics** | لوحة Firebase → Crashlytics → إعدادات التنبيهات |

مصدر DSN الوحيد: `version.properties` → `sentryDsn` (يتولد منه `wameed_version.py`).

## 2. ما الذي يُلتقط اليوم (جهة ويندوز)

- كل استثناء غير معالج (`sys.excepthook` + `threading.excepthook`) — يُرسل مع flush.
- أعطال مصنفة عبر `report_windows_issue(category, ...)`: فشل استقبال/إرسال ملف،
  فشل فحص/تنزيل/تثبيت تحديث، فشل قاعدة الجدار الناري... كلٌّ بوسوم
  `wameed.category` و`wameed.report_id` و`wameed.phase`.
- التعقيم: عناوين IP تُقص إلى `x.x.x.x → x.x.x.x`، ومسارات المستخدم تُستبدل —
  انظر `_sanitize_for_telemetry`.

## 3. ما الذي **لا يمكن** التقاطه من داخل التطبيق

فشل ما قبل الإقلاع (مثل `Failed to load Python DLL` في بنية onefile القديمة) يقع
قبل أن يعمل أي سطر بايثون — لا يمكن لأي كود في التطبيق الإبلاغ عنه. العلاج منعُه
من الأساس: منذ 3.0.1 البناء onedir فاختفى هذا الصنف. القاعدة العامة: **أعطال
المثبّت/الإقلاع تُعالج بالوقاية والتوقيع الرقمي، لا بالتقارير.**

## 4. قواعد التنبيه المطلوبة في Sentry (تُنشأ مرة واحدة)

### لماذا القاعدة الحالية «لا تغطي كل شيء ولا ترسل دائمًا»

القاعدة الموجودة (Send a notification for high priority issues) لها ثلاثة حدود
مقصودة في تصميم Sentry:

1. **الأولوية**: تشترط أن يكون الـ Issue بأولوية **عالية** — التحذيرات والرسائل
   متوسطة/منخفضة الأولوية لا تُرسل بريدًا.
2. **التكرار**: البريد يُرسل عند *أول* ظهور للمشكلة؛ تكرار نفس الخطأ لاحقًا لا
   يعيد الإرسال إلا بعد فاصل القاعدة الزمني — هذا مقصود لمنع إغراق بريدك.
3. **التجميع**: إعدادات حسابك الشخصية قد تجمّع الإيميلات في ملخصات (Digest) —
   افحص Settings → Notifications → Email Routing/Workflow.

### القاعدة الشاملة (أنشئها يدويًا — الرابط المباشر)

افتح: <https://management-system-th.sentry.io/alerts/new/issue/?project=wameed-windows>

- **WHEN**: `A new issue is created`
- **THEN**: `Send a notification to Suggested Assignees` أو
  `Send a notification to Member → بريدك`
- **Action interval**: 5 minutes
- الاسم: `Email on any new issue` → **Save Rule**

> أدوات Sentry MCP تقرأ القواعد وتفحصها لكنها لا تنشئها — الإنشاء من الواجهة فقط.

بقية القواعد المقترحة:

1. **Issue Alert — أي مشكلة جديدة**: `A new issue is created` → Action:
   `Send a notification to Email` (بريدك). هذه أهم قاعدة — بدونها لا يصلك شيء.
2. **Issue Alert — عودة مشكلة**: `The issue changes state from resolved to unresolved` → بريد.
3. **Metric Alert — موجة أعطال**: `count() of errors > 20 في الساعة` → بريد.
4. تأكد من **Verify email** في حسابك، وأن إشعارات المشروع غير مكتومة
   (User Settings → Notifications).

> Sentry MCP (مُصادَق) يتيح لـ Claude فحص الأحداث والقواعد الموجودة — إنشاء
> القواعد نفسه يتم من واجهة Sentry فقط.
>
> **نتيجة فحص 2026-09-05**: المنظمة `management-system-th`، المشروع
> `wameed-windows`. توجد قاعدة فعّالة «Send a notification for high priority
> issues» (بريد للأعضاء النشطين). حدث اختبار أُرسل ووصل خلال ثوانٍ
> (WAMEED-WINDOWS-9) وأطلق القاعدة فعلاً — خط الأنابيب يعمل. سبب غياب
> الإيميلات سابقًا: **لم يصل أي حدث خطأ خلال 90 يومًا أصلًا** (أعطال DLL كانت
> قبل الإقلاع فلا يمكن التبليغ عنها). يبقى إنشاء قاعدة «أي Issue جديد» يدويًا
> لتغطية الأخطاء منخفضة الأولوية.

## 5. المطلوب في Firebase (أندرويد)

Firebase Console → المشروع → إعدادات التنبيهات (Alerts):

- فعّل بريد **Crashlytics: New fatal issue** و**Velocity alerts** (عطل يضرب
  نسبة كبيرة من الجلسات) لحسابك.
- الإغلاق القسري المفاجئ على الهواتف يظهر هنا (ANR + crashes) — كود التطبيق
  يلتقطها فعلاً عبر `WameedCrashReporter`.

## 6. دورة التعامل مع بلاغ

1. البريد يصل ومعه `wameed.report_id` (ويندوز) أو issue id (أندرويد).
2. المستخدم يرى نفس المعرف في نافذة الخطأ — اطلبه منه عند التبليغ اليدوي.
3. ابحث بالمعرف في اللوحة → السياق الكامل (الإصدار، المرحلة، ملخص الشبكة).
4. السجل المحلي التفصيلي: `%USERPROFILE%\.wameed\logs\receiver.log` (ويندوز).

## 7. فجوات معروفة (مرشحة للتنفيذ لاحقًا)

- المثبّت (Inno) لا يبلّغ عن فشل التثبيت — يمكن إضافة سطر سجل محلي يُرفع مع أول
  تشغيل ناجح.
- لا يوجد "نبض" دوري يخبرك أن الإصدار الجديد يعمل عند المستخدمين — يمكن إضافة
  حدث `session_start` بعيّنة منخفضة.
